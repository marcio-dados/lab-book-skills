# Chapter 9: The Logical Architecture

## Core Idea
Each of the four principles introduces one architectural component: domain ownership extends domain interfaces with analytical data-sharing; data-as-a-product introduces the **data (product) quantum** as the architecture quantum; the self-serve platform becomes a **multiplane platform**; and federated computational governance embeds a **sidecar** into every data product to execute policy as code.

## Frameworks Introduced
- **Data Product as Architecture Quantum**: (from *Building Evolutionary Architectures*) the smallest independently-deployable unit with high functional cohesion and all structural elements required for its function — applied to data products as data mesh's opinionated unit of architecture, scaling by *adding and connecting more data products*, not by growing one.
- **Three Structural Component Types of a data product**: Code (transformation-as-code, interfaces-as-code, policy-as-code), Data & Metadata, Platform (infrastructure) dependencies.
  - How: use this triad as a completeness checklist for any data product design — missing any one of the three means it isn't autonomous.
- **Three Platform Planes** (introduced in miniature here, detailed in Ch 10): Data Infrastructure (Utility) Plane, Data Product Experience Plane, Mesh Experience Plane — deliberately *not* called "layers," since any authorized user can access any plane directly (no strict hierarchical access).
- **Embedded Computational Policy components**: Data product sidecar (executes cross-cutting policy in the data product's runtime context), Data product computational container (bundles code+data+sidecar as one deployable unit), Control port (standardized API to configure policies and invoke privileged operations like GDPR's "right to be forgotten").

## Key Concepts
- **Input data port / Output data port**: internal mechanism to consume from upstream sources vs. externally addressable API to serve data — data mesh's term for "port," used interchangeably with "interface."
- **Data product sidecar**: a process sharing the data product's execution context, injected at deploy time, that executes domain-agnostic cross-cutting concerns (policy execution, standardized discovery/SLO APIs) — same pattern as a service-mesh sidecar (e.g., Istio), applied to data instead of network traffic.
- **"I rarely use the term metadata"**: the author deliberately avoids treating metadata as one generic bucket — it's split into typed, contractual concerns (documentation, schema, SLOs, statistical properties) each with its own life cycle, generated by the data product itself, not extracted after the fact by an external catalog.
- **Interdomain analytical data dependency**: a data product explicitly declares and controls its own upstream sources and how it consumes them (event subscription vs. time-triggered query) — the dependency lives in the consuming data product, not in a central pipeline config.

## Mental Models
- **"Form ever follows function"** (Sullivan, epigraph): the chapter derives architecture *from* each principle's requirement, not from picking components first — a useful posture when justifying why data mesh has the shape it does.
- **Active data (product) vs. passive data (artifact)**: a defining distinction — a data product *runs code* to maintain and serve its data; a file or table sitting in a warehouse is inert. This is why pipelines dissolve into internal transformation code rather than staying an external artifact.
- **Planes, not layers**: rejects strict layering (data-plane/control-plane borrowed from network routing) in favor of "experience" as the organizing idea — a plane's users can bypass it and go straight to a lower plane when the higher one doesn't yet support their need (with the expectation that the gap gets "harvested" back into the standard plane later).

## Anti-patterns
- **Calling everything about a dataset "metadata"**: conflates semantically distinct concerns (schema, SLOs, statistical profile, lineage) into one catch-all, which leads to fragile, centralized catalog architectures over time.
- **Cleansing data downstream as a norm**: if a data product's transformation code needs a cleansing step for data it consumes, that's a signal something upstream needs fixing — dirty data should be the exception (a documented gap in the contract, like `listener subscriptions` lacking payment info by design), not routine downstream repair.
- **Centralized catalog extracting metadata after the fact**: the "big departure" data mesh makes is that the data product itself generates and owns its metadata as part of its interface contract — an external system inferring metadata post-hoc is the old pattern being replaced.

## Key Takeaways
1. Every data mesh architectural component traces back to exactly one of the four principles — there's no component introduced "just because."
2. The data (product) quantum is the axis of scale-out: data mesh grows by adding independently-deployable quanta, never by growing one shared component.
3. A data product is active (runs code), unlike passive data artifacts (files/tables) — this is the structural reason pipelines disappear as external components.
4. Metadata is not one thing — treat documentation, schema, SLOs, and statistical properties as distinct, contractual, product-generated concerns.
5. Platform planes are not layers: users may cross planes directly; the platform's job is to make the higher-abstraction path so easy that nobody needs to.
6. At time of writing (per the book), most of these components (data quantum, sidecar, control port, mesh/data-product experience planes) are experimental, custom-built per organization — no public reference implementation existed yet.
